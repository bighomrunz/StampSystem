# Phase 2.5 — โหมดคีย์มือ (เสร็จแล้ว ทดสอบกับฐานข้อมูลจริงผ่าน)

เปิดใช้งานสองจังหวะตามที่เจ้าของร้านสั่งเมื่อ 16 ต.ค. 2026
**ช่วงที่ 1** พนักงานคีย์มือ ลูกค้ายังไม่ต้องมี LINE → **ช่วงที่ 2** เปิด LIFF เต็มระบบ

## นโยบายที่ตกลงแล้ว

| เรื่อง | ที่ตัดสินใจ |
|---|---|
| ระบุตัวลูกค้าช่วงคีย์มือ | ชื่อ + เบอร์โทรเต็ม (ค้นด้วยชื่อหรือเบอร์บางส่วนก็เจอ) |
| ผูกบัญชี LINE ตอนเปิดช่วงที่ 2 | พนักงานผูกหน้าร้าน โดยสแกน QR ของลูกค้าจาก LIFF |
| รูปถ่ายบัตรกระดาษ | **ยังไม่ต้อง** ใช้ PIN เจ้าของร้านเป็นตัวคุมก่อน (บัตรจริงเก็บไว้ที่ร้านเป็นหลักฐาน) |
| อายุแต้มที่ย้ายมา | เท่าแต้มใหม่ (`StampExpiryMonths`) นับจากวันย้าย |

หมายเหตุ: ข้อนี้เปลี่ยนคำตอบเดิมใน README เรื่อง "ลูกค้าที่ไม่ใช่ LINE ไม่รองรับ"
— ตอนนี้**รองรับผ่านโหมดคีย์มือ** (ไม่ได้ทำระบบเบอร์โทร + OTP) ต้องแก้ README ด้วย

## สองข้อที่ยึดไว้ ไม่ยอมหย่อน

1. **แต้มจากการขายยังผูกออเดอร์จริงเสมอ** การ "เลือกลูกค้า" เปลี่ยนแค่วิธีระบุตัวลูกค้า
   ยังต้องมีออเดอร์ที่รับเงินแล้ว และออกแต้มได้ครั้งเดียวต่อออเดอร์
   (ช่วงคีย์มือไม่มี QR มายืนยันว่าลูกค้าอยู่ตรงนั้น การผูกออเดอร์คือสิ่งเดียวที่เหลือ
   ไว้กันพนักงานแจกแต้มให้คนรู้จัก — `audit_logs` จึงบันทึก `Source: ManualSelect` หรือ `Qr`
   ไว้ให้รายงาน Phase 4 จับอัตราการออกแต้มแบบเลือกมือที่สูงผิดปกติ)
2. **แต้มจากบัตรกระดาษเป็น `Adjust` + PIN เจ้าของร้านเท่านั้น** และ**ย้ายได้ครั้งเดียวต่อคนตลอดกาล**

## ทำเสร็จแล้ว (build ผ่าน, unit test 104 ตัวผ่าน)

- `Customer`: `LineUserId` เป็น nullable, เพิ่ม `Phone`, `Source` (Counter/Line),
  `CreatedByStaffId`, `ConsentSource` (Counter/Liff)
- `StampTransaction`: เพิ่ม `ApprovedByStaffId`, `AdjustKind`
- `AppDbContext`: partial unique index สองตัว
  - `ux_customers_line_user_id` — unique เฉพาะแถวที่ `line_user_id IS NOT NULL`
  - `ux_stamp_transactions_card_migration` — unique ที่ `customer_id` เฉพาะ `adjust_kind = 'CardMigration'`
- `PhoneNumber` — normalize/validate/format เบอร์โทร
- `StaffAuthService.VerifyOwnerPinAsync` — PIN เจ้าของร้านเท่านั้น (ผู้จัดการอนุมัติไม่ได้)
- `CustomerAdminService` — ค้นหา, สร้างสมาชิกที่เคาน์เตอร์ (บังคับยืนยันว่าแจ้ง PDPA แล้ว),
  แก้ชื่อ/เบอร์, `LinkLineAccountAsync` (ย้าย `line_user_id` มาที่ระเบียนเดิม
  อนุญาตเฉพาะเมื่อระเบียนฝั่ง LINE ยังไม่มีประวัติแต้ม เพราะ ledger เป็น append-only ห้ามย้าย)
- `StampService` — แยก `EarnCoreAsync` ให้ทางเดิม (QR) และทางใหม่
  (`EarnForOrderByCustomerAsync`) ใช้กฎชุดเดียวกัน, เพิ่ม `MigratePaperCardAsync`
  (เพดานย้ายไม่เกิน `StampsPerReward - 1` แต้ม บัตรเต็มให้แลกฟรีหน้าร้านแทน)
- DI ลงทะเบียน `CustomerAdminService` แล้ว

## ทำเพิ่มรอบที่สอง

- **migration `Phase25ManualMembers`** สร้างแล้ว (ยังไม่ได้ลง DB)
  แก้มือหนึ่งจุด: EF สร้าง `source` มาพร้อม `defaultValue: ""` ซึ่ง parse เป็น enum ไม่ได้
  เปลี่ยนเป็น `"Line"` เพราะลูกค้าที่มีอยู่ก่อนหน้านี้ทุกคนสมัครผ่าน LINE
- **API** — `GET/POST /api/customers`, `GET/PUT /api/customers/{id}`,
  `POST /api/customers/{id}/paper-card`, `POST /api/customers/{id}/link-line`,
  `POST /api/orders/{id}/stamps-by-customer`
- **หน้าจอพนักงาน** — หน้า `/Customers` (ค้นหา เพิ่มสมาชิก ดูบัตร ย้ายบัตรกระดาษ ผูก LINE),
  เมนู "สมาชิก" บนแถบบน, และ `customer-picker.js` ที่หน้าขายกับหน้าออเดอร์เรียกใช้ร่วมกัน
  (เลือกลูกค้าจากรายชื่อ หรือสแกน QR ถ้าลูกค้าผูก LINE แล้ว)
- **unit test เพิ่ม 33 ตัว** (รวม 137 ตัว ผ่านหมด) — `PhoneNumber`, สมาชิกที่สมัครหน้าร้าน,
  ความยินยอมทางเคาน์เตอร์, เพดานการย้ายบัตร และการแท็ก `AdjustKind`
- **PDPA** — เพิ่มเบอร์โทรและหัวข้อ "การสมัครที่เคาน์เตอร์" ในหน้า `/liff/privacy`
  และทำ [PDPA-COUNTER-NOTICE.md](PDPA-COUNTER-NOTICE.md) สำหรับพิมพ์ติดที่เคาน์เตอร์
- แก้ README ข้อ "ลูกค้าที่ไม่ใช้ LINE" ให้ตรงกับการตัดสินใจใหม่แล้ว

## ผลการทดสอบกับฐานข้อมูลจริง (17 ต.ค. 2026)

migration `Phase25ManualMembers` ลงฐานข้อมูลแล้ว ตรวจ schema หลังลงเสร็จ

- `customers.line_user_id` เป็น nullable และ unique index กลายเป็น
  `ux_customers_line_user_id ... WHERE (line_user_id IS NOT NULL)` ตามที่ต้องการ
- `ux_stamp_transactions_card_migration ... WHERE adjust_kind = 'CardMigration'` ถูกสร้าง
- `source` มี default `'Line'` ให้แถวที่มีอยู่ก่อนหน้า
- ข้อมูลเดิม (staff, menu, devices, audit) ยังอยู่ครบหลัง migration

ไล่ flow จริงผ่านทั้งหมด

| สิ่งที่ทดสอบ | ผล |
|---|---|
| สร้างสมาชิกโดยไม่ยืนยันว่าแจ้ง PDPA | ถูกปฏิเสธ |
| เบอร์โทรผิดรูปแบบ (5 หลัก) | ถูกปฏิเสธ "ต้องมี 9 ถึง 10 หลัก" |
| สร้างสมาชิกชื่อไทย + เบอร์ `081-234-5678` | สำเร็จ เก็บเป็น `0812345678` แสดงเป็น `081-234-5678` |
| ค้นด้วยเบอร์บางส่วน `0812` และค้นด้วยชื่อไทย | เจอทั้งสองแบบ |
| ขายอเมริกาโน่ 2 + น้ำเปล่า 1 แล้วเลือกลูกค้าออกแต้ม | ได้ 2 แต้ม (น้ำเปล่าไม่นับ), `notified: false` เพราะยังไม่มี LINE |
| ออกแต้มซ้ำออเดอร์เดิม | ถูกปฏิเสธ "ออเดอร์นี้ออกแต้มไปแล้ว" |
| ย้ายบัตรกระดาษด้วย PIN ผิด | ถูกปฏิเสธ "PIN ของเจ้าของร้านไม่ถูกต้อง" |
| ย้ายบัตรเต็มใบ 10 แต้ม | ถูกปฏิเสธ ให้แลกฟรีหน้าร้านแทน |
| ย้ายบัตร 7 แต้ม + PIN เจ้าของร้าน | สำเร็จ ยอดรวม 9 หมดอายุ 17/10/2027 |
| ย้ายซ้ำ | ถูกปฏิเสธ "ย้ายบัตรกระดาษไปแล้ว" |
| ผูกบัญชี LINE เข้าระเบียนที่คีย์มือ | สำเร็จ ลูกค้าเห็นบัตรใบเดิมที่มี 9 แต้ม |
| ผูกซ้ำ | ถูกปฏิเสธ |
| ออกแต้มด้วย QR หลังผูกบัญชีแล้ว | สำเร็จ ยอดเป็น 10 |
| ผลรวม ledger เทียบ `customer_balances` | ตรงกัน |
| `Adjust` ของการย้ายบัตร | มี `approved_by_staff_id` และไม่มี `order_id` ถูกต้อง |

### บั๊กที่เจอจากการรันจริงและแก้แล้ว

**หน้าบัตรของลูกค้าพังหลังพนักงานผูกบัญชี** — การผูกบัญชีจะปิดระเบียนฝั่ง LINE เดิม
แต่ cookie ของลูกค้ายังชี้ไปที่ระเบียนนั้น ทำให้ `/api/liff/me` ตอบ
"ไม่พบบัญชีสมาชิก" เป็น error 400 และลูกค้าขอ QR ไม่ได้จนกว่าจะล้าง cookie เอง

แก้โดย: ฝั่งเซิร์ฟเวอร์ถ้าเซสชันชี้ไปบัญชีที่ถูกปิด จะ sign out แล้วตอบ 401
(`ResolveOrSignOutAsync`) และฝั่งหน้าบัตรจะล็อกอินใหม่อัตโนมัติหนึ่งครั้งเมื่อเจอ 401
ผลคือลูกค้าแค่เห็นหน้าโหลดใหม่แล้วเจอบัตรใบเดิมที่แต้มครบ
