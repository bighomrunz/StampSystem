## ตารางที่เพิ่ม (migration `Phase2Membership`)

- `customers` — `public_id` (ใช้ใน QR), `line_user_id` (unique), `consent_version`, `consent_at`,
  `last_used_qr_step`, `is_active`
- `customer_balances` — ยอดแต้มคงเหลือ หนึ่งแถวต่อลูกค้า ใช้คอลัมน์ระบบ `xmin` ของ PostgreSQL
  เป็น concurrency token กันการออกแต้ม/แลกแต้มซ้อนกัน
- `stamp_transactions` — ledger แบบ append-only (`Earn`/`Redeem`/`Void`/`Expire`/`Adjust`)
  พร้อม `expires_at` ต่อรายการ Earn เพื่อรองรับ FIFO ใน Phase 3
- `orders.customer_id` — ผูกออเดอร์กับลูกค้าตอนสแกน QR

**กฎที่บังคับในระดับฐานข้อมูล ไม่ใช่แค่ในโค้ด**

```sql
CREATE UNIQUE INDEX ux_stamp_transactions_order_earn
    ON stamp_transactions (order_id) WHERE type = 'Earn';
```

หนึ่งออเดอร์ออกแต้มได้ครั้งเดียว แม้พนักงานสองเครื่องกดพร้อมกัน ตัวที่สองจะชน unique index
แล้วได้ข้อความ "ออเดอร์นี้ออกแต้มไปแล้ว"

## QR ลูกค้าหมุนเวียนอย่างไร

```
token = "CS1" . base64url(public_id) . timeStep . base64url(HMAC-SHA256(secret)[0..15])
timeStep = unix_seconds / 30
```

- ยอมรับคลาดเวลาได้ ±1 step (รวมหน้าต่างใช้งานจริงประมาณ 60-90 วินาที)
- **ใช้ได้ครั้งเดียว** เก็บ `customers.last_used_qr_step` ไว้ ถ้า step ที่สแกนมา
  น้อยกว่าหรือเท่ากับค่าที่เคยใช้ จะถูกปฏิเสธ
- `POST /api/customers/resolve` (ดูยอดก่อนออกแต้ม) **ไม่** ใช้ step ทิ้ง
  ส่วน `POST /api/orders/{id}/stamps` เป็นตัวที่ใช้ step
- secret อ่านจาก `Qr:Secret` ถ้าไม่ตั้งใน production แอปจะไม่บูต
  (ใน Development จะสุ่มให้ชั่วคราวและ log เตือน)

นี่คือส่วนที่แก้ปัญหาเดิมโดยตรง: ภาพ QR ที่แคปไว้หรือส่งต่อให้เพื่อนจะหมดอายุใน 30 วินาที
และถ้าถูกใช้ไปแล้วก็ใช้ซ้ำไม่ได้

## เงื่อนไขการออกแต้ม (ทั้งหมดตรวจฝั่งเซิร์ฟเวอร์)

1. ร้านเป็นฝ่ายสแกน QR ของลูกค้า — ไม่มี endpoint ที่ลูกค้าเรียกเพื่อให้ตัวเองได้แต้ม
2. ออเดอร์ต้องมีสถานะ `Paid` แล้ว
3. ออเดอร์ต้องอยู่ในวันทำการเดียวกัน (สแกนภายหลังได้ แต่ข้ามวันไม่ได้)
4. วันทำการนั้นต้องยังไม่ปิดยอด
5. ออเดอร์นั้นต้องยังไม่เคยออกแต้ม
6. ลูกค้าต้องให้ความยินยอม PDPA เวอร์ชันปัจจุบันแล้ว
7. จำนวนแต้ม = ผลรวม `quantity` ของบรรทัดที่ `earns_stamp_snapshot = true` และไม่ใช่แก้วรางวัล
8. วันหมดอายุ = สิ้นวันตามเวลาไทยของ (วันทำการ + `StampExpiryMonths`), `0` = ไม่หมดอายุ

## PDPA

- ลูกค้าต้องกดยอมรับก่อนใช้บัตร ระบบเก็บ `consent_version` + `consent_at`
- ถ้าเปลี่ยนค่า `Pdpa:Version` ลูกค้าทุกคนต้องยินยอมใหม่ (ของเก่าถือว่าไม่ครอบคลุม)
- ยังไม่ยินยอม = ขอ QR ไม่ได้ ดังนั้นร้านก็ออกแต้มให้ไม่ได้
- ถอนความยินยอมได้เองจากหน้าบัตร ระบบจะปิดบัตร ลบชื่อ รูปโปรไฟล์
  และ**แทนที่ LINE user id ด้วยค่าสุ่ม** เพื่อให้ไม่เหลือข้อมูลที่ระบุตัวบุคคล
  แต่ยัง**เก็บ ledger ไว้**เป็นหลักฐานทางบัญชี (แต้มเดิมใช้ต่อไม่ได้ และถ้ากลับมาสมัครใหม่จะได้บัตรใบใหม่)
- ข้อความแจ้งอยู่ที่หน้า `/liff` และ `/liff/privacy` ทั้งสองหน้าแสดงเวอร์ชันข้อความกำกับไว้

## การแยกเซสชันลูกค้ากับพนักงาน

ใช้ cookie และ authentication scheme แยกกันคนละตัว (`cs_staff` กับ `cs_customer`)
และ API อยู่คนละ group กัน ยืนยันด้วยการทดสอบแล้วว่า cookie พนักงานเรียก `/api/liff/*` ได้ 401
และ cookie ลูกค้าเรียก API พนักงานไม่ได้

> หมายเหตุทางเทคนิค: group policy ของ ASP.NET Core เป็นแบบ "บวกกัน"
> ถ้าเอา LIFF ไปอยู่ใต้ group `/api` ที่ใส่ policy `Staff` ไว้ ลูกค้าจะติด policy พนักงานไปด้วย
> จึงต้องแยก `app.MapGroup("/api/liff")` ออกมาต่างหาก

## ผลการทดสอบกับของจริง (16 ต.ค. 2026)

unit test 104 ตัวผ่านหมด (เพิ่มจาก Phase 1 มา 48 ตัว ครอบคลุม QR token, PDPA, วันหมดอายุ,
การ validate ID token ของ LINE, ข้อความ push)

ไล่ flow จริงกับ PostgreSQL 18.1 ครบ 21 ขั้น ผลที่ยืนยันแล้ว

- ลูกค้าใหม่ล็อกอิน → ระบบขอความยินยอม → ยินยอมเวอร์ชันผิดถูกปฏิเสธ → ยินยอมถูกต้องผ่าน
- ยังไม่ยินยอม ขอ QR ไม่ได้
- ขาย "อเมริกาโน่ 2 + น้ำเปล่า 1" ได้ **2 แต้ม** (น้ำเปล่าตั้งไว้ว่าไม่นับแต้ม)
- วันหมดอายุออกมาเป็น 16/10/2027 (12 เดือน นับถึงสิ้นวันตามเวลาไทย)
- `resolve` ดูยอดได้โดย QR ยังใช้ออกแต้มต่อได้ (ตรงตามที่ออกแบบ)
- QR เดิมใช้ซ้ำ → "QR นี้ถูกใช้ไปแล้ว", ออเดอร์เดิมออกแต้มซ้ำ → "ออเดอร์นี้ออกแต้มไปแล้ว"
- QR ที่แก้ MAC → "QR นี้ไม่ถูกต้อง อาจเป็นภาพที่แคปมาจากเครื่องอื่น"
- QR มั่ว ๆ ได้ 400 ไม่มี 500 เลยใน log
- ยกเลิกออเดอร์ที่ออกแต้มแล้ว → เขียนรายการ `Void` ย้อนแต้มอัตโนมัติ (ยอด 3 → 2)
- ออเดอร์ที่ยังไม่รับเงิน ออกแต้มไม่ได้
- ผลรวม ledger เท่ากับ `customer_balances.stamps` ของลูกค้าทุกคน
- ถอนความยินยอมแล้วเรียก API ต่อได้ 401 และข้อมูลระบุตัวตนถูกลบจริง

### บั๊กที่เจอจากการรันจริงและแก้แล้ว

1. **QR เพี้ยนทำให้เกิด 500** — `new Guid(bytes)` โยน `ArgumentException` (ไม่ใช่ `FormatException`)
   เมื่อความยาวไม่ใช่ 16 ไบต์ ทำให้ endpoint สแกนพังเป็น 500 ถ้ามีใครยิง token มั่ว ๆ เข้ามา
   แก้โดยเช็กความยาวเองและจับทั้งสอง exception
2. **antiforgery token หมดอายุหลังลูกค้าล็อกอิน** — token ผูกกับตัวตนของผู้เรียก
   หน้าบัตรดึง token ตอนยังไม่ล็อกอิน พอล็อกอินเสร็จแล้วกด "ยอมรับ" จะถูกปฏิเสธทันที
   แก้โดยเพิ่ม `GET /api/liff/csrf` และให้หน้าบัตรขอ token ใหม่หลังล็อกอิน (พร้อม retry หนึ่งครั้ง)
3. **ถอนความยินยอมแล้วยังเหลือ LINE user id** — ขัดกับข้อความที่แจ้งลูกค้าไว้ในหน้า privacy
   แก้โดยแทนที่ด้วยค่าสุ่มตอนถอนความยินยอม
