# เปิดใช้งานเฉพาะการสแตมป์ (stamp-first)

เจ้าของร้านสั่งเมื่อ 20 ต.ค. 2026 ว่าจะ **เปิดใช้แค่การสแตมป์ก่อน** และระบบที่ทำไว้
"ดูเป็น POS เกินไป" พร้อมชี้ปัญหาที่เจอจาก reward card เดิมใน LINE คือ
**เวลาสแตมป์ผิดต้องไปทำบัตรใหม่ขึ้นมาเลย**

## สิ่งที่เปลี่ยน

### 1. หน้าสแตมป์เป็นหน้าหลัก

`/` คือหน้าสแตมป์ (`Pages/Stamp.cshtml`) ใช้งานสามขั้นจบ

1. เลือกลูกค้า — ค้นชื่อหรือเบอร์ หรือสแกน QR (ถ้าลูกค้าผูก LINE แล้ว)
2. กดจำนวนแก้ว (1-6)
3. เลือกช่องทางชำระ แล้วกด **สแตมป์**

ยอดเงินเป็นช่องไม่บังคับ เว้นว่างได้ในช่วงที่ยังไม่ใช้ระบบคิดเงิน

หน้าขายเต็ม (เลือกเมนู, QR พร้อมเพย์, Pending/ยืนยันรับเงิน) ย้ายไป `/Pos`
และแถบเมนูแสดงให้เฉพาะผู้จัดการ พนักงานหน้าร้านเห็นแค่ **สแตมป์ · สมาชิก · ออเดอร์**

### 2. ขายเร็ว ไม่ต้องเลือกเมนู

`POST /api/stamp` ทำสองอย่างในคำขอเดียว: สร้างออเดอร์แบบขายเร็วแล้วออกแต้มให้ลูกค้า

ออเดอร์ขายเร็วมีบรรทัดเดียวชื่อ "ขายเร็ว N แก้ว" ไม่มี `MenuItemId`
ถือว่ารับเงินแล้วทันที (พนักงานกดหลังรับเงิน) จึงไม่มีขั้น Pending

**ยังรักษาหลักข้อ 2 ของ README ไว้** — แต้มยังผูกกับออเดอร์จริงที่มีพนักงาน อุปกรณ์ เวลา
และวันทำการ ไม่มี endpoint ที่ออกแต้มลอย ๆ และหนึ่งออเดอร์ยังออกแต้มได้ครั้งเดียว
(unique index ที่ฐานข้อมูล) สิ่งที่ตัดออกคือการเลือกเมนูกับการคิดเงิน ไม่ใช่ตัวการผูกออเดอร์

### 3. แก้สแตมป์ผิดได้ ไม่ต้องออกบัตรใหม่

`ledger` เป็น append-only การแก้จึงเป็นการ **เพิ่มรายการ** ไม่ใช่ลบของเก่า
บัตรของลูกค้าเป็นใบเดิมตลอด ประวัติยังเห็นทั้งรายการที่ผิดและรายการที่แก้

| สถานการณ์ | วิธีแก้ | ใครทำได้ | รายการที่เขียนลง ledger |
|---|---|---|---|
| สแตมป์เกิน / ลูกค้าคืนแก้ว | ปุ่ม "สแตมป์ผิด ยกเลิก" ที่หน้าสแตมป์ หรือฟอร์มแก้แต้มที่หน้าสมาชิก | **พนักงาน** (ไม่ต้องใช้ PIN) | `Adjust/Correction` จำนวนลบ |
| ลืมสแตมป์ / สแตมป์ขาด | ฟอร์มแก้แต้มที่หน้าสมาชิก ใส่จำนวนบวก | **ผู้จัดการ** (ต้องใส่ PIN) | `Adjust/Correction` จำนวนบวก |
| **สแตมป์ผิดคน** | ปุ่ม "สแตมป์ผิดคน" ที่หน้าออเดอร์ แล้วเลือกคนที่ถูก | **ผู้จัดการ** (ต้องใส่ PIN) | `Void` ฝั่งผิด + `Adjust/Correction` ฝั่งถูก ผูกออเดอร์เดิมทั้งคู่ |

เหตุผลของการแบ่งสิทธิ์: **ลดแต้มเสียหายกับร้านไม่ได้** พนักงานจึงแก้เองได้ทันทีหน้าลูกค้า
แต่ **เพิ่มแต้มคือการสร้างมูลค่าขึ้นมา** จึงต้องมีผู้อนุมัติ (ตามที่เจ้าของร้านเลือกไว้)

เงื่อนไขที่ระบบบังคับ
- ต้องระบุเหตุผลทุกครั้ง เก็บไว้ใน `note` และ `audit_logs`
- ยอดคงเหลือติดลบไม่ได้ (ลดเกินยอดจะถูกปฏิเสธพร้อมบอกยอดที่มี)
- แก้ได้ครั้งละไม่เกิน 50 แต้ม
- ย้ายแต้มได้เฉพาะวันทำการที่ยังไม่ปิดยอด และย้ายซ้ำออเดอร์เดิมไม่ได้
- ออกแต้มทับออเดอร์ที่ออกแต้มแล้วจะถูกปฏิเสธ พร้อมบอกให้ใช้ปุ่มย้ายแต้มแทน
- rate limit แยกเป็น policy `correct` (30 ครั้ง/นาที) ไม่ใช้ร่วมกับ login

## ผลการทดสอบ (20 ต.ค. 2026)

unit test 157 ตัวผ่านหมด (เพิ่มจาก 137 มา 20 ตัว ครอบคลุมกฎการแก้แต้มและขายเร็ว)

flow จริงกับ PostgreSQL ผ่านทั้งหมด

| ทดสอบ | ผล |
|---|---|
| สแตมป์ 2 แก้ว ไม่ใส่ยอดเงิน | ได้ 2 แต้ม ออเดอร์ `20261020-0001` |
| สแตมป์ 1 แก้ว ใส่ยอด 55 บาท | ได้ 1 แต้ม ยอดรวม 3 |
| ยกเลิกสแตมป์ล่าสุด (พนักงาน ไม่ใช้ PIN) | ยอดเหลือ 2 |
| ลดแต้มโดยไม่ใส่เหตุผล | ถูกปฏิเสธ |
| ลด 10 แต้มจากยอด 3 | ถูกปฏิเสธ "ลดได้ไม่เกินยอดคงเหลือ ลูกค้ามี 3 แต้ม" |
| เพิ่มแต้มโดยไม่มี PIN ผู้จัดการ | ถูกปฏิเสธ |
| เพิ่มแต้มด้วย PIN ผู้จัดการ | สำเร็จ |
| ย้ายแต้มผิดคนโดยไม่มี PIN | ถูกปฏิเสธ |
| ย้ายแต้มด้วย PIN ผู้จัดการ | ย้าย 1 แต้มจาก ก ไป ข สำเร็จ |
| ย้ายซ้ำ / ออกแต้มทับออเดอร์เดิม | ถูกปฏิเสธ พร้อมบอกทางแก้ |
| สแตมป์โดยไม่เลือกลูกค้า / 0 แก้ว | ถูกปฏิเสธ |
| เหตุผลภาษาไทยใน ledger | เก็บถูกต้อง |
| ผลรวม ledger เทียบยอดคงเหลือของทุกคน | ตรงกัน |

### บั๊กที่เจอจากการรันจริงและแก้แล้ว

**rate limit ของการแก้แต้มแคบเกินไป** — ตอนแรกผูก endpoint แก้แต้มกับ policy `login`
(10 ครั้ง/นาที/IP) ซึ่งใช้ร่วมกับการล็อกอินพนักงาน ทำให้ช่วงที่หน้าร้านยุ่งแล้วแก้แต้มหลายครั้ง
จะติด 429 แยกเป็น policy `correct` (30 ครั้ง/นาที) แล้ว

## ยังไม่ได้ทำ

- ปุ่ม "สแตมป์ผิด ยกเลิก" ที่หน้าสแตมป์ยกเลิกได้เฉพาะครั้งล่าสุดที่กดในหน้านั้น
  ถ้าเปลี่ยนหน้าไปแล้วต้องไปแก้ที่หน้าสมาชิกหรือหน้าออเดอร์
- ยังไม่มีตัวเลือกปิดหน้า `/Pos` และ `/DailyClose` ทั้งหมดใน `ShopSettings`
  ตอนนี้แค่ซ่อนจากแถบเมนูของพนักงาน (ผู้จัดการยังเข้าได้)
- Phase 3 (แลกรางวัล, FIFO expiry, เพดานแต้ม) ยังไม่เริ่ม
