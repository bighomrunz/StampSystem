# การย้ายบัตรคะแนนกระดาษเดิมเข้าระบบ

สรุปนโยบายที่เจ้าของร้านตัดสินใจเมื่อ 16 ต.ค. 2026 ตัวงานจริงอยู่ใน **Phase 4** ตาม README
แต่มีบางส่วนที่ต้องเตรียมไว้ตั้งแต่ Phase 3 (ดูหัวข้อ "ผลต่อ Phase 3")

## นโยบายที่ตกลงแล้ว

| เรื่อง | ที่ตัดสินใจ |
|---|---|
| วิธีย้าย | ย้ายรายคน ตอนลูกค้าสมัครสมาชิก LIFF ที่หน้าเคาน์เตอร์ **ไม่มี bulk import** |
| ผู้อนุมัติ | Owner กด PIN หน้างานทันที (แบบเดียวกับการยกเลิกออเดอร์ที่ใช้ PIN ผู้จัดการ) |
| อายุแต้มที่ย้ายมา | เท่ากับแต้มปกติ คือ `StampExpiryMonths` (ค่าตั้งต้น 12 เดือน) นับจากวันที่ย้าย |
| ลูกค้าที่ไม่ใช้ LINE | ไม่รองรับ ให้ใช้บัตรกระดาษแลกจนหมดภายในวันตัด แล้วจบ — **ไม่ทำระบบเบอร์โทร + OTP** |

ข้อสุดท้ายตอบคำถามที่เปิดไว้ท้าย README ไปหนึ่งข้อแล้ว

## ขั้นตอนหน้าร้าน

1. **วันเปิดระบบ: หยุดปั๊มบัตรกระดาษใหม่ทันที** กระดาษใช้ได้แค่ "แลก" หรือ "ย้าย" ไม่งอกเพิ่ม
2. ประกาศ **วันตัด** ล่วงหน้า (แนะนำ 60 วัน) หลังวันนั้นไม่รับบัตรกระดาษทุกกรณี
3. **บัตรที่เต็มแล้ว → ให้แลกเครื่องดื่มฟรีไปเลย ไม่ต้องย้าย** แล้วเก็บบัตรไว้ที่ร้าน
   ผลพลอยได้คือความเสี่ยงต่อคนเหลือไม่เกิน `StampsPerReward - 1` แต้มโดยอัตโนมัติ
4. **บัตรที่ยังไม่เต็ม → ย้ายครั้งเดียวต่อลูกค้าหนึ่งคนตลอดกาล** (ถ้ามีหลายใบ รวมเป็นรายการเดียว)
   1. ลูกค้าสมัคร LIFF และกดยอมรับ PDPA ให้เสร็จก่อน
   2. พนักงานเขียนชื่อ LINE + วันที่ลงบนบัตรด้วยปากกา
   3. ถ่ายรูปบัตรเข้าระบบ
   4. กรอกจำนวนแต้ม → Owner กด PIN อนุมัติ → ระบบบันทึก `Adjust` และเพิ่มแต้มทันที
   5. **ตัดมุมบัตรหรือปั๊มว่า "ย้ายแล้ว"** แล้วเก็บบัตรไว้ที่ร้าน

ข้อ 3 กับ 4 รวมกันคือหัวใจ: เพดานความเสียหายถูกจำกัดด้วยตัวระบบ ไม่ต้องพึ่งวินัยพนักงาน

## สิ่งที่ต้องสร้าง (Phase 4)

ตอนนี้มีแค่ enum `StampTransactionType.Adjust` ที่ยังไม่มีใครเรียกใช้ ของที่ขาดคือ

- `StampTransaction.ApprovedByStaffId` — ปัจจุบันมีแค่ `StaffId` (คนคีย์) ไม่มีช่องผู้อนุมัติ
  (เทียบกับ `Order.VoidApprovedByStaffId` ที่มีอยู่แล้ว)
- ตาราง `CardMigration`
  - `CustomerId` + **unique index** → บังคับ "หนึ่งคนย้ายได้ครั้งเดียว" ที่ระดับฐานข้อมูล
    เหมือนที่ทำกับ `ux_stamp_transactions_order_earn`
  - `StampsApproved`, `PhotoPath`, `EnteredByStaffId`, `ApprovedByStaffId`, `ApprovedAt`, `Note`
  - `StampTransactionId` ชี้ไปที่รายการ `Adjust` ที่เกิดขึ้น
- การเก็บรูปถ่าย — ระบบยังไม่มีการอัปโหลดไฟล์เลย
  - เก็บไฟล์ **นอก `wwwroot`** และเปิดดูผ่าน endpoint ที่ต้องล็อกอินเท่านั้น
  - รูปบัตรมีชื่อลูกค้าเขียนอยู่ = ข้อมูลส่วนบุคคล ต้องอยู่ในขอบเขต PDPA เดียวกัน
    และต้องถูกลบเมื่อลูกค้าถอนความยินยอม
- หน้าจอฝั่งพนักงาน: ปุ่ม "ย้ายบัตรกระดาษ" ต่อจากการสมัครสมาชิก
- รายงาน: จำนวนการย้ายต่อพนักงานต่อวัน และยอดแต้มรวมที่ย้ายเข้า (ไว้จับความผิดปกติ)
- `AuditLog` ต้องมีรายการ `stamp.migrate` พร้อม `ApprovedByStaffId` และเลขอ้างอิงรูป

## ผลต่อ Phase 3 (ต้องทำตอนนั้น ไม่ใช่ Phase 4)

ช่วง dual-run ร้านยังรับบัตรกระดาษมาแลกเครื่องดื่มฟรี แก้วฟรีใบนั้น
**ไม่มีแต้มในระบบและไม่มีรายการใน ledger** ถ้าปล่อยไว้จะกลายเป็นบรรทัดราคา 0 ที่อธิบายไม่ได้
ทำให้ยอดขายรายเมนูและ anomaly report ของ Phase 4 อ่านไม่ออก

ดังนั้นตอนออกแบบ `Redemption` ใน Phase 3 ต้องมีช่องระบุที่มาของการแลก

```
Redemption.Source = Stamps | PaperCard
```

- `Stamps` — ตัดแต้มจาก ledger ตามปกติ
- `PaperCard` — ไม่ตัดแต้ม (เพราะไม่มีแต้มในระบบ) แต่ **ต้องมีเหตุผลและ PIN ผู้จัดการ**
  และนับแยกในรายงาน ใช้ได้จนถึงวันตัดเท่านั้น

## ยังต้องตอบก่อนเริ่ม Phase 3

คำถามข้อแรกท้าย README ยังเปิดอยู่และ Phase 3 ต้องใช้:
